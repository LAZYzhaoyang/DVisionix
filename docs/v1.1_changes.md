# v1.1 变更与迁移指南

> v1.1 是**稳定性与工程优化**版本：修复了 v1.0.0 中 20 项已核实缺陷，
> 并把「官方配置能否真的跑起来」变成 CI 门禁。架构与对外概念没有变化，
> 但有若干**会改变训练结果、输出格式或 API 行为**的改动，本文给出完整清单。
>
> 完整规划与逐条证据见 [CodePlan](../CodePlan.md)；逐版本摘要见 [CHANGELOG](../CHANGELOG.md)。

## 1. 必须关注的破坏性变更

### 1.1 检测损失：GIoU / L1 权重显式化，默认只算 GIoU

**旧**：`use_giou: true` 时实际是 `GIoU + L1`，`use_giou: false` 时是 `2 × L1`
（实现里无条件多加了一份 L1，参数名与真实训练信号不符）。

**新**：用显式权重，默认只算 GIoU（与 FCOS 论文 / torchvision 参考实现一致）。

```yaml
loss:
  type: "fcos_detection"
  strides: [4, 8, 16, 32]
  scales: [0, 32, 64, 128, 256, 1000000000.0]
  giou_weight: 1.0     # 新增：GIoU 权重（默认 1.0）
  l1_weight: 0.0       # 新增：L1 权重（默认 0.0，即不参与）
```

- 旧的 `use_giou` 仍可使用，但会发出 `DeprecationWarning`，并按其**字面意图**迁移
  （`true` → GIoU、`false` → L1）；与显式权重同时给出会直接报错。
- 同时修正了**正样本归一化**：回归项不再随 batch size 与特征层数漂移。
- ⚠️ **v1.0.0 的 checkpoint 不可直接续训**，既有学习率等超参需要重新标定。

### 1.2 `history.csv` 的 epoch 指标改为 `val_` 前缀

```text
v1.0.0:  accuracy, f1, precision, recall, train_acc, train_loss, val_loss
v1.1:    val_accuracy, val_f1, val_precision, val_recall, train_acc, train_loss, val_loss
```

原因：旧实现里 `fit()` 在评估之外**又调用了一次** `on_validation_epoch_end()`，
第二次是在已重置的累加器上计算，得到全 0 并覆盖正确值。

**如果你有解析 `history.csv` 的脚本，请同步改名。**

### 1.3 resume 现在会校验一致性

`Trainer.load_checkpoint` 默认**拒绝**：

- 配置哈希不匹配（`config_hash`）
- 任务类型 / 模型类型不匹配
- 纯 `state_dict`（不是完整 checkpoint）
- `model_state_dict` 含非张量条目

确需跨配置续训时显式放行：

```python
trainer.load_checkpoint(path, model, allow_config_mismatch=True)
```

### 1.4 checkpoint 反序列化的信任策略

反序列化 pickle 等于执行任意代码，而预训练权重通常来自第三方：

```python
from dvisionix.training import load_backbone

# 默认安全模式（weights_only=True）：只允许张量与基本容器
load_backbone(model, "third_party.pth")

# 文件确实由本项目产出、且携带优化器 / RNG 等非张量状态时才这样写
load_backbone(model, "our_last.pt", trusted=True)
```

`Trainer.load_checkpoint` 因为断点续训必须恢复非张量状态，默认 `trusted=True`；
**不要对来源不明的文件使用默认值**，可用 `trusted=False` 走安全模式。

### 1.5 裁剪契约：尺寸不足时默认报错

```python
RandomCrop((224, 224))                    # 输入小于 224 时抛 ValueError
RandomCrop((224, 224), on_small="pad")    # 右下补零
RandomCrop((224, 224), on_small="resize") # 直接缩放（几何版不支持该选项）
```

旧行为是**静默返回错误尺寸**（`RandomCrop` 返回原图、`CenterCrop` 经负索引切片
返回更小的图）。内置预设管线不受影响（resize 后尺寸恒满足）。

### 1.6 检测训练管线先放大再裁剪

旧管线先把图 resize 到目标尺寸、再执行同尺寸裁剪，随机偏移恒为 0，
**数据增强完全没有生效**。现在训练时先 resize 到 1.1× 再裁剪（与分类预设一致）。

### 1.7 合成数据 train / val 已拆分

旧实现中 train 与 val 共用文件名序列，**验证集就是训练集的前 N 张**，
所有 demo 的 `val_loss` / `val_acc` 都含数据泄漏。现在使用不同 split 前缀与独立随机种子，
且数据可复现。指标会明显变差，属预期修正。

### 1.8 顶层导入改为惰性

```python
from dvisionix.config import Config   # 不再拉起 torch（实测 3~4s → ~0.12s）
```

**带来的语义变化**：组件的注册发生在各子模块被导入时。使用注册表前请显式导入：

```python
import dvisionix.models      # 填充 MODELS / BACKBONES / NECKS / HEADS / LAYERS / LOSSES
import dvisionix.training    # 填充 TASKS
import dvisionix.metrics     # 填充 METRICS
from dvisionix.registry import MODELS
```

顶层便捷导出（`dvisionix.build_model(...)`、`dvisionix.MODELS`）仍然可用，
它们会按需导入所需子模块。

## 2. 新增配置项

```yaml
training:
  # EMA（v1.0.0 只能编程式使用，配置里写了也不生效）
  ema:
    enabled: true
    decay: 0.999
    decay_warmup_epochs: 5
    swap_for_validation: true
    save_final: true          # 训练结束导出 ema_last.pt

  # 数据加载性能
  pin_memory: false
  persistent_workers: false   # 仅在 num_workers > 0 时生效
  prefetch_factor: null
  non_blocking: false         # CPU→GPU 异步搬运，需配合 pin_memory 才有收益
```

以下键 v1.0.0 已在 `base.yaml` 中提供，但 schema 未登记，每次运行都会打出
「未知 training 配置键」的误导性告警；现在已登记：
`compile`、`channels_last`、`export_best_onnx`。

## 3. 关键修复速览

| 领域 | 修复 |
|---|---|
| 官方配置 | `simclr_synthetic`、`centernet_synthetic`、`yolov10_synthetic` 三个配置在 v1.0.0 **无法训练**，现已修复；17/17 可训练配置全部通过端到端门禁 |
| `decode()` 契约 | `centernet` / `nmsfree_yolo` 缺少 `iou_threshold`，验证阶段必然抛 `TypeError`；现已统一，并由契约测试守护 |
| DDP | 聚合会把检测的 `(boxes, scores, labels)` 拍平；`validate()` 无 DDP 分支且不触发验证回调（EMA 权重交换失效） |
| DINO | 用 `feats[0].shape * 4` 当图像尺寸，官方配置下偏差 2 倍，去噪分支与主分支坐标系不一致 |
| mask | `ToTensor` 可能把 mask 转成 float，破坏 `CrossEntropyLoss` 的 long 契约 |
| mask AP | 首图空预测时目标尺寸退化为 `(1, 1)`，指标完全失真 |
| ONNX | 嵌套输出直接崩溃；导出会永久改变调用者模型的设备与 train/eval 状态 |
| 梯度累积 | 尾窗不足一个完整窗口时梯度被系统性低估 |
| 打包 | `config/defaults/*.yaml` 不进 wheel，非 editable 安装下 `Config.from_default()` 必然失败 |
| 文档契约 | `out_indices` 越界静默取模、`MetricCollection` 重名静默覆盖、TensorBoard 标量从未写入、库代码用 `print` 等 |

## 4. 性能

新增 `tools/benchmark.py`（固定输入、可复现、可隔离测峰值内存）：

```bash
python tools/benchmark.py --list
python tools/benchmark.py --scenario all --json bench.json
python tools/benchmark.py --scenario pq --isolate   # 独立进程以测干净峰值内存
```

本机（CPU / torch 2.12）实测的前后对比：

| 场景 | v1.0.0 | v1.1 | 说明 |
|---|---|---|---|
| 匈牙利匹配（300 查询 × 30 GT） | 13 652 ms | **18.6 ms** | 旧实现把代价矩阵补成方阵后跑纯 Python O(n²m)，规模被放大两个数量级 |
| 全景质量 PQ（512×512 / 25 实例） | 582 ms | **123 ms** | 旧实现会实体化 `(P, G, H*W)` 布尔张量（1024×1024 下约 400MB） |
| EMA 开销（占训练总耗时） | 17.1% | **1.44%** | 改为原地更新 + 缓存张量引用 + 只处理浮点张量（目标 < 3% ✅） |
| 只导入 config 的耗时 | ~3–4 s | **0.10 s** | 顶层导入改为惰性（完整 `import dvisionix.models` 仍需 2.6 s，那是 torch 的成本） |
| mAP（100 图 × 20 框） | 173 ms | 180 ms | 未优化，实测不是瓶颈，如实记录 |
| TaskAligned 分配（3 层 20×20） | 1.1 ms | 1.0 ms | 未优化，实测不是瓶颈 |

所有优化都附带**数值一致性验证**（与朴素参考实现对拍）：PQ / SQ / RQ 与 mAP
在优化前后逐位一致，匹配结果经穷举验证仍为最小代价。

## 5. 打包与安装

依赖与版本的**唯一来源是 `pyproject.toml`**（`setup.py` 已删除，
`requirements.txt` 只是指向它的指针）：

```bash
pip install -e .              # 核心依赖
pip install -e .[export]      # ONNX 导出与验证
pip install -e .[models]      # timm
pip install -e .[datasets]    # albumentations
pip install -e .[coco]        # pycocotools
pip install -e .[metrics]     # torchmetrics
pip install -e .[full,dev]    # 全部能力 + 开发工具
```

解释器：`requires-python = ">=3.10"`，CI 覆盖 3.10 / 3.11 / 3.12
（classifier 已列到 3.14，3.13 / 3.14 为实验性支持）。

```bash
pytest tests/                          # 全量（含官方配置端到端门禁）
pytest tests -m "not slow"             # 快速反馈
pytest tests/test_e2e_configs.py -q    # 只跑官方配置端到端门禁
pytest tests/test_model_contracts.py -q
pytest tests/test_training/test_ddp_cpu.py -q   # CPU 双进程 DDP 一致性

```

CI 门禁顺序：`ruff` → `black` → `mypy`（信息性）→ 快速测试 → 全量测试 + 覆盖率
（≥90%）→ wheel 构建与干净环境安装 → `pip-audit`（信息性）。

- `mypy` 与 `pip-audit` 目前是**信息性**门禁（原因与升级条件见 CodePlan 7.6）。
- Windows 提示：请先 `conda activate dvisionix` 再运行测试。
